**웹 pending handshake · 양쪽 S6DP-02.** 웹의 bearer nonce는 JS 메모리·sessionStorage·localStorage·IndexedDB에 넣지 않는다. 발급/회전/폐기의 순서는 다음과 같다. strict Origin+custom-header의 POST start가 설치를 아직 만들거나 회전하지 않고 서버 CSPRNG pending-cookie와10분 pending operation을 발급한다. 이어 custom-header GET state가 실제 pending-cookie 수신을 확인하고 비밀 아닌 operation_id·CSRF 토큰·단계만 반환한다. 쿠키가 없으면 쓰기를 진행하지 않고 COOKIE_REQUIRED 안내다. POST commit은 cookie+CSRF+operation_id·정확한 payload hash를 검사한다. 웹 발급/회전/복구 결과의 secret/hash/nonce는 본문에 넣지 않고 Set-Cookie로만 적용한다. GET state는 ACTIVE/PENDING/REVOKED/EXPIRED/NONE 등 제한된 상태와 새 CSRF만 제공하고 현재 installation 식별·설정은 유효 cookie가 있을 때만 제공한다.

pending operation은 HttpOnly pending-cookie hash·설치/구 capability hash·종류·payload hash에 결속한다. 다른 브라우저/다른 Origin/다른 payload의 같은 operation은 거부한다. 결과 본문만 유실됐지만 새 cookie가 적용됐으면 GET state가 현재 ACTIVE/version 및 해당 operation 완료를 알려 종료한다. Set-Cookie가 미적용됐으면 기존 pending-cookie로 같은 commit/결과 확인을 반복해 서버 영수증의 새 cookie만 재적용한다. 구 capability는 일반 API 인증에 재사용하지 않는다. 성공 확인 전 pending-cookie를 지우지 않고 완료 ACK 이후에만 지운다. 새로고침은 cookie로 같은 operation을 찾고, 두 탭은 동일 설치에 한 pending operation만 허용하며 다른 탭은409 OPERATION_PENDING 후 기존 상태 확인에 합류한다.10분 만료 뒤 불명확한 것은 UNKNOWN/재연결 필요로 남기고 자동 새 설치 발급을 하지 않는다. 웹 JS에는 비밀 아닌 operation_id/CSRF만 일시 보관한다. native는 앞 절의 SecureStore pending/nonce/구 capability 보관 방식이며 두 전송 모드를 섞지 않는다. 이 handshake는 발급 전 확인·새로고침·두 탭·cookie 차단·헤더 미적용·본문 유실·구/새 cookie·다른 Origin/브라우저 replay를 각각 시험한다.

**설정 자동 정리와 CAS · Codex S6DP-03.** 기존 `private.installation_settings`를 사용해 catalog_impact의 설치 수와 SQL30 자동 정리를 유지한다. 새 migration은 settings_revision 및 설정 변경 이력, BEFORE/AFTER UPDATE trigger를 추가한다. 사용자 저장뿐 아니라 SQL30의 자동 sector_ids 정리도 같은 트랜잭션에서 revision을 올리고 제거된 비활성 sector ID/당시 표시명/시각·revision을 남긴다. 안내는 ‘비활성화되어 관심 섹터에서 제외됨’이며 재선택이나 삭제 전 상태로 복원을 요구하지 않는다. 이력은30일 상한이고 일반 알림 발송 내역과 구별한다. 기존 함수 본문을 바꾸지 않는 trigger 방식이다. 새 설정 저장은 먼저 catalog_head share lock, 그 뒤 설치/설정 row lock 순서로 최신 head와 expected settings_revision을 검사한다. 비활성화는 기존 head update lock→설정 row lock 순서를 유지한다. 구 head/구 revision 저장은409이며 자동 덮어쓰기를 하지 않는다. 관리자 영향 미리보기 이후 관심 목록이 바뀌면 기존 impact digest 재검사가 충돌을 감지해야 한다. 비활성화→오래된 저장, 저장→비활성화, 두 설치/두 탭, 영향 설치 수와 제거 이력/revision의 원자성을 실제 DB 시험한다.

**연결 해제/초기화 · Codex S6DP-04.** 이번 기능의 정확한 이름은 ‘이 기기 서버 연결 해제’와 ‘로컬 연결 정보 초기화’다. 개인정보 전체 삭제 기능이 아니며 그렇게 표시하지 않는다. 서버 연결 해제는 확인 뒤 같은 pending operation으로 설치 revoked_at 설정·구 secret 인증 차단·알림3종 false/관심 섹터 비움·view ticket 무효화·미발송 합성 delivery 취소를 원자 처리한다. 설치 row는 FK용 최소 tombstone으로 남기고 raw 조회와 이미 확정한 QA 일별 집계는 원래30일/1년 TTL대로 유지한다. 이를 DATA_PURGE_COMPLETE가 아닌 CAPABILITY_REVOKE로 ledger에 기록한다. 원시/일별 집계의 누락을 만들지 않으므로 coverage를 거짓으로 연장하거나 정상 과거 조회를 재집계하지 않는다. 실제 개인정보 삭제/백업 소거는 출시 전 별도 정책·기능 게이트이며6D 완료로 표시하지 않는다.

## 10. r3 최초 두 탭 bootstrap 보완

**Codex r2 S6DP-02.** 설치 cookie가 없는 첫 start 이전부터 웹의 전체 발급·회전·폐기·복구·ACK·로컬 초기화 sequence를 제품/환경 전용 Web Lock `judoju-news:local:installation:v1`로 직렬화한다. 허용된 웹 Origin은127.0.0.1:8084 하나이며 다른 Origin/port의 앱이 같은 cookie를 대상으로 쓰는 경로는 열지 않는다. lock 안에서 최신 서버 state와 별도 제품 namespace의 작은 localStorage generation fence를 먼저 읽는다. Web Locks나 fence의 영속 읽기/쓰기를 지원하지 않으면 bootstrap/회전/폐기 쓰기를 중지하고 안내하며 느슨한 대체 구현을 쓰지 않는다. 유효 cookie의 읽기와 기사·기기 저장의 기존 경로는 독립이다.

fence에는 무작위 operation_id/generation, 종류·phase만 기록한다. 이것은 인증 권한이 아니며 secret/nonce/hash/installation_id/CSRF/설정·기사 내용은 넣지 않는다. 서버는 fence의 값만으로 발급 결과/capability를 제공하지 않는다. 첫 POST start **이전**에 START_DISPATCHED를 영속 기록하고, 서버 cookie 확인→commit→최신 state의 같은 operation 완료→ACK 확인까지 lock을 유지한다. 같은 브라우저 다른 탭은 lock 획득 후 이 fence를 복원하며 새로운 start 대신 같은 operation의 제한된 state/결과 확인에만 합류한다. POST start는 client의 비밀 아닌 operation_id도 받아 유일하게 등록한다. 이미 존재하는 start에 새 pending nonce/cookie를 다시 발급하지 않는다. 정확한 pending cookie가 있으면 기존 단계를 확인하고, cookie가 없으면 bare operation_id만으로 비밀/cookie를 재발급하지 않고 UNKNOWN_COOKIE_REQUIRED로 중지한다.

timeout·abort·탭 닫힘/새로고침으로 lock이 풀려도 fence는 지우지 않는다. UNKNOWN_START/UNKNOWN_COMMIT에서는 새로운 generation/start/다른키 mutation을 보내지 않는다. 새 탭의 state가 NONE이어도 오래된 응답이 아직 처리 중일 수 있으므로 발급을 반복하지 않는다. 기한 경과만으로 fence를 초기화하지 않고, 같은 operation의 cookie/state가 일치해 결과가 확정될 때만 진행한다. 일치 확인이 불가능하면 UNKNOWN으로 중단하며 정상 연결/초기화 성공을 표시하지 않는다. 이후의 확정적 START 봉인과 명시적 COMMIT 연결 포기 절차는 아래 r4 계약을 따른다. 이 웹 bootstrap UNKNOWN을 §9의 단순 로컬 초기화만으로 우회하지 않는다. 새 generation은 아래 r4 서버 봉인 결과가 확인된 뒤에만 시작한다. 사용자가 앱 밖에서 cookie/브라우저 데이터를 지우는 동작까지 안전성을 보장한다고 주장하지 않는다.

웹에서 선행 cookie 쓰기 전송이 아직 미확정이면 state가 ACTIVE로 보이는 것만으로 fence를 해제하거나 새 generation을 시작하지 않는다. 그 상태에서는 같은 Set-Cookie 영수증을 다시 적용하는 mutation도 보내지 않고 읽기 state 확인만 하며 UNKNOWN으로 중단한다. §9의 cookie 재적용은 선행 전송이 미적용/종료됐음이 실제로 확인된 경우에만 허용한다. 단순 abort/timeout/탭 종료나 기한 경과를 미적용·종료 근거로 쓰지 않는다. cookie 제거 ACK도 cookie 쓰기이므로 같은 조건을 적용한다. 늦은 응답의 자동 cookie 쓰기를 client generation 검사만으로 막을 수 있다고 가정하지 않는다.

서버 commit도 기대 generation·pending cookie·operation 종류·기존 session 관계를 다시 검사한다. BOOTSTRAP인데 이미 다른 유효 session이 있거나 session/pending의 세대가 다르면409로 중지하고 새 session cookie를 쓰지 않는다. 같은 operation 결과의 Set-Cookie만 재적용할 수 있으며, 한 웹 sequence의 모든 cookie 쓰기는 위 lock/fence 경계를 따른다. state GET과 일반 설정 GET은 session/pending cookie를 변경하지 않는다. 최종 완료가 확인되기 전에 다음 sequence를 시작하지 않기 때문에 불명확한 구 start/commit이 남은 상태에서 새 발급을 진행하지 않는다. 지연 응답 때문에 세대 관계가 불명확해지면 중단 경로를 택한다.

인수 시험은 cookie/fence가 모두 없는 두 탭 동시 start, start/commit 응답 순서 역전·지연, start와 commit 사이 reload/탭 종료, Set-Cookie 적용 뒤 본문 유실, cookie 미적용, fence 쓰기 실패/손상, lock 미지원, UNKNOWN 뒤 재진입을 포함한다. 기대값은 **동일한 하나의 발급 결과로 수렴하거나 UNKNOWN으로 중단**, 두 번째 설치 발급/다른 generation의 확정 session 덮어쓰기/새 키 자동 재전송0이다. 정상 두 탭에서는 start 호출 하나와 동일 session을 확인하고, 미확정 시험에서는 새 start0을 확인한다. transport가 불명확하면 시간 경과를 성공한 종료로 세지 않는다. 네이티브는 별도 단일 provider queue와 SecureStore pending을 사용하며 웹 Web Lock을 쓰는 것으로 네이티브 검증을 대신하지 않는다.

**Claude r2 S6DP-06.** 설치 HTTP allowlist에는 새41+ 함수만 포함하며 `m0_create_installation`·`m0_rotate_installation`·`m0_update_settings` 등 fixture RPC는 넣지 않는다. route→RPC 이름 고정과 web JSON의 secret/hash 부재를 시험한다. local24시간 capability가 만료되어 복구가 불가능한 ‘재연결’은 사용자 확인 뒤 **새 설치/알림 기본값**을 만드는 뜻이며 과거 설정 복원으로 표시하지 않는다. 다른 기기의 설정이나 이전 설치의 선호를 새 설치로 옮기지 않는다. 이 기기 기사 저장은 보존한다. 운영 설치의 장기 수명·복구 정책은 여전히 출시 전 별도 게이트다. 상세 view ticket은 공개 응답에서 실제 읽은 version_id를 보내고 서버의 현재 version과 일치할 때만 발급·수락한다.

## 11. r4 제안 · 서버 봉인에 의한 확정적 복구

이 절은 Claude r3 S6DP-07(P2)을 해소하기 위한 **추가 검수 전 제안**이다. 기본 검수3판본을 소진했으므로 사용자에게 이 동일 case의 두 역할 추가 판본1개 승인을 받기 전에는 외부 검수를 더 전송하거나 제품 구현을 시작하지 않는다. 나머지 승인 범위/이전 원문/모델/회차 제한은 변경하지 않는다.

**START만 있었거나 등록 여부도 모르는 경우.** 고정 경로 `POST start-seal`은 exact 웹 Origin/custom-header, 요청 형식/rate와 비밀 아닌 generation UUID를 검사하고 DB에서 그 generation을 원자적으로 봉인한다. 아직 row가 없으면 SEALED_START tombstone을 insert하고, STARTED이며 설치 생성이 없으면 같은 row를 SEALED_START로 바꾼다. start/commit/seal은 같은 generation row의 unique/lock 규칙을 사용한다. 이 결과는 secret/hash/설치 ID 없이 SEALED_START와 generation·서버 확인시각만 반환한다. 미래에 도착한 start/commit은 봉인 row를 보고409로 종료하며 새 cookie/capability를 발급하지 않는다. 동시 commit이 먼저 끝났다면 START 봉인을 성공으로 가장하지 않고 COMMITTED를 반환해 아래 절차로 보낸다. 미등록을 조회한 뒤 별도로 새 발급하는 TOCTOU 방식은 금지한다.

이는 타 설치의 인증 폐기나 설정 변경 권한이 아니다. 설치가 생기기 전 generation의 발급 가능성만 봉인하므로 초기 cookie가 없는 브라우저도 복구할 수 있다. 봉인된 최소 generation 중복 차단 tombstone에는 secret/설정/기사/설치 고유집합을 남기지 않으며 이후 재발급 방지에 사용한다. 실제 개인정보 삭제 완료로 표시하지 않는다. 서버가 SEALED_START를 확정한 뒤 Web Lock 안에서 fence에 그 결과를 기록하고 새 generation을 시작할 수 있다. 시간 경과 자체나 client abort는 봉인 증거가 아니다. seal 응답 유실은 같은 generation의 멱등 봉인/상태 확인으로 처리한다.

**COMMIT이 끝났을 수 있으나 capability를 복구할 수 없는 경우.** 자동 새 발급은 계속 금지한다. 먼저 서버가 같은 generation의 terminal 상태와 원래 pending deadline 만료를 DB 시각/row lock으로 확인한다. 사용자가 ‘이전 설정을 복구하지 못할 수 있음 · 이전 서버 데이터 삭제 아님’ 안내에 동의하면 `POST generation-forget`이 그 generation을 SEALED_FORGOTTEN으로 원자 봉인하고 이후 start/commit/복구 cookie 발급을 차단한다. 등록·처리 중이면 봉인을 성공으로 반환하지 않는다. 이 조작은 기존 설치의 secret을 제공하거나 해당 설치를 인증·삭제/폐기하지 않으며, 남을 수 있는 고아 local 설치는 기존24시간 capability TTL로 만료된다. 이미 받은 유효 cookie로 기존 설치를 계속 사용하는 별도 정상 경로를 이 요청이 인증 없이 수정하지 않는다. 서버 봉인 결과 확인 뒤에만 사용자가 새 설치/알림 기본값을 선택할 수 있다. 이전 설정 복원·서버 폐기·개인정보 삭제 성공으로 표시하지 않는다. 운영에서 고아 푸시 토큰/설치의 처리까지 완성됐다는 뜻이 아니며 실제 푸시 활성화 전 별도 게이트다.

**늦은 HTTP Set-Cookie와 세대 분리.** 이미 전송된 응답 헤더 자체를 서버 봉인이 취소한다고 가정하지 않는다. 실제 cookie 이름은 `judoju_install_pending_<generation>` 및 `judoju_install_session_<generation>`으로 분리한다. bootstrap/rotation의 각 operation generation마다 다른 이름을 사용한다. late old response는 옛 이름만 쓸 수 있으므로 새 generation의 cookie를 덮지 못한다. 웹의 비밀 아닌 fence envelope에는 pending_generation과 confirmed_generation 포인터만 추가한다. API 요청은 이 포인터의 expected generation을 명시하고 서버는 정확히 그 이름의 cookie와 DB의 generation/secret version만 검사한다. cookie prefix에서 임의의 첫 값/최신 값/사용 가능한 다른 세대를 자동 선택하지 않는다. 봉인/포기된 generation은 복구 commit 권한으로 쓰지 않는다. 정상 회전도 새 generation cookie가 확인된 후에만 confirmed_generation을 교체하고 기존 구 secret은 일반 API에서 거부한다. 늦은 JS 응답도 generation 검사로 무시한다.

cookie 삭제/ACK/cleanup은 확인한 **정확한 옛 cookie 이름**만 만료시키며 wildcard/전역 cookie 제거로 새 session을 지우지 않는다. state GET은 cookie를 쓰지 않는다. 만료/봉인된 다른 세대 cookie는 인증에서 무시하고 필요한 경우 사용자 연결을 유지한 채 전용 cleanup으로 정확한 이름만 정리한다. 헤더 크기/동시 cookie 세대 상한을 두고 상한 초과는 COOKIE_CLEANUP_REQUIRED이지 새로운 발급 반복이 아니다. 설치 cookie의 HttpOnly/Strict/host-only/전용 Path, JS 비밀 저장 금지와 관리자 cookie 무시는 유지한다. generation 포인터만으로는 어떤 설치 권한도 얻지 못한다.

**추가 인수 기대값.** 최초 start 응답 전 reload→fence만 남음→미등록 또는 STARTED 원자 봉인→단일 새 generation 정상 연결, start와 seal 동시 실행, commit과 seal 경합에서 SEALED_START/COMMITTED를 정확히 구분, seal 응답 유실/같은 키 재확인, SEALED 이후 늦은 start/commit409를 검사한다. UNKNOWN_COMMIT은 서버 deadline/terminal 확인 이전에 진행하지 않고, 확인 후 사용자 연결 포기→SEALED_FORGOTTEN→새 설치 기본값·북마크 유지 경로를 검사한다. 옛 start/commit/ACK의 Set-Cookie가 새 generation 확정 뒤 도착해도 옛 이름만 바뀌고 새 설정/confirmed_generation/secret이 유지되어야 한다. 자동 재발급0·봉인 후 옛 commit0·다른 세대 session 덮어쓰기0이며, 서버 확정 복구가 가능한 일반적인 reload는 영구 잠금 상태로 끝나지 않아야 한다. 이 기대값은 아직 구현·실행으로 통과한 것이 아니다.
