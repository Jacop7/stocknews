## 1. 이번 계획의 범위와 제작 원칙

기준은 이번 폴더의 서비스v1.6·어드민v1.1·뉴스상세v1.1·매체부록·공통운영계약v1.0과 bundle-manifest.json이다. 구판은 이력이다. v1.2는 저장·알림 이동, 기사 등록 시 섹터 선택, 어드민 섹터 관리, 관련 종목 웹뷰를 4~6단계에 반영했다. 어드민 사이드바·기사의 대표 섹터와 관련 섹터·관심 섹터 관리 위치는 서비스 기획안 v1.6의 앱 화면·어드민 웹과 이 문서 8·9절을 기준으로 한다. 실제 저장소 초기화·패키지 설치·Supabase 생성·계정 연결·서버 배포는 이번 문서 작성으로 실행하지 않았다.

현재 상위 작업 폴더에는 기존 자료·기획 문서와 봉인된 모델 실행계획이 있다. 제품용 `judoju-news` 폴더·Git 저장소·앱·Supabase 프로젝트는 이번 문서 개정으로 생성하지 않았다. 제품 구현 착수 시 상위 계획의 SHA·역할·모델·적용 범위를 복원 검증하고 새 제품 루트에 맞는 범위를 확인한다. 기존 유효 계획이 있는데 새로 없는 것으로 처리하지 않는다.

### 신규 프로젝트 구성 — 식자재 관리앱과 분리 {#new-project}

공통 운영 계약의 project-isolation은 사용자 확정 제약이다. 제품 루트는 `C:/Users/jacop/주식/judoju-news`에 새로 만들고 그 안에서만 새 Git 이력과 전용 remote를 시작한다. 식자재 관리앱을 fork·복사하거나 그 저장소 안의 기능 브랜치로 만들지 않는다. 기존 앱의 코드·공통 패키지·환경파일·DB/데이터·인증·worker·CI/CD를 가져오거나 경로 연결하지 않는다. 기존 HTML 시안·스프레드시트·뉴스 기획은 주도주뉴스의 요구/이관 자료로만 사용한다. 상위 폴더의 이 프로젝트용 검수·모델 계획 복원은 식자재 앱 제품 자원을 재사용한다는 뜻이 아니다.

| 구성 | 새로 만드는 주도주뉴스 전용 자원 |
| --- | --- |
| 저장소·브랜치 | 새 Git 저장소/remote, 자체 main 및 짧은 기능 브랜치. 기존 앱 Git 이력·submodule·symlink 연결 없음 |

0~1단계에 기존 제품 경로와 신규 제품 root/remote를 구분하고, 2단계에 앱 식별자·EAS 연결을 확인한다. 4단계 DB/worker 연결 전과 12단계 배포 전에는 root/remote·Supabase project ref/DB 대상·EAS projectId/앱 식별자·Docker 자원 이름/포트·배포/로그/백업 대상을 `project_resource_manifest`에 기록해 대조한다. 계획이 아닌 실제 대상 값을 확인하며 비밀키 원문은 기록하지 않는다. 기존 식자재 앱 대상이 하나라도 연결돼 있으면 해당 연결/배포를 차단하고 새 자원을 지정한다. 설치된 공용 개발 도구까지 다시 설치하거나 기존 앱을 삭제/중지하는 요구는 아니다. 실제 자원 생성·유료 계약·스토어 등록은 착수 시 권한·비용 조건을 확인해 실행한다.

`project_resource_manifest`는 로컬 Supabase project_id·API/DB/Studio 등 활성 포트·컨테이너/volume·제품 식별 검사 결과도 포함한다. 충돌이면 기존 서비스는 건드리지 않고 신규 제품 설정의 포트를 바꾸며, 출처를 확인하지 못한 localhost endpoint에는 migration/seed/쓰기 작업을 실행하지 않는다. 0단계는 root/remote 계획과 미생성 자원 상태,2단계는 앱 식별자·로컬 설정,4단계는 DB/worker 실제 대상,12단계는 배포 대상을 확인한다. 제품 간 분리 증거인 이 manifest의 버전·해시를 환경 간 배포 증거인 release_manifest가 참조하며 P08/P12에서 함께 대조한다. 아직 만들지 않은 자원은 PENDING으로 기록하고 해당 연결/배포 게이트를 통과시키지 않는다.

### 기술 구성

- 하나의 Git 저장소에 Expo 앱, 관리자 웹, 봇, DB 변경 이력을 함께 둔다.
- 이용자 프론트는 우선 Android·iOS 앱이다. 관리자 프론트는 웹이다. 별도의 일반 이용자 웹서비스는 후속 범위로 구분한다.
- Android와 iOS는 같은 Expo·React Native 코드로 개발하고 양쪽을 초기에 빌드·시험한다.
- 관리자 웹은 React·Next.js·TypeScript를 기본안으로 둔다. 관리자 서버 렌더링·API가 필요하면 같은 배포에서 처리한다.
- DB·관리자 인증·접근 권한·공개 데이터 API는 Supabase를 중심으로 구성한다.
- 긴 뉴스·AI 작업은 TypeScript·Node 기반 작업 실행부를 Docker로 운영하는 안을 우선 검증한다. 별도 범용 API 서버를 동시에 중복 구축하지 않는다.
- 제품 코드에는 TypeScript를 사용하고 공통 데이터 형식·검증 규칙을 공유한다. AI 모델 제공사는 별도 선택한다.
- 도구·SDK 버전은 착수 시 지원 조합을 확인해 고정한다. 문서에 임의의 최신 버전 번호를 적지 않는다.

이하 ‘선택안’은 구현을 위한 권장 구성이다. 공급처 계약·호스팅·실제 자동 게시 활성화 같은 미정 사업 결정은 서비스 기획안 v1.6의 구분을 유지한다.

P0는 나머지 구현의 기반, P1은 수동 운영 가능한 제품, P2는 자동 운영, P3는 출시 완성 단계다. 앱 빌드·광고·푸시 호환성의 작은 기술 검증은 2단계에서 앞당겨 시행하고, 실제 서비스 기능 완성은 11단계에서 진행한다.

독립된 작업은 기다리지 않아도 된다. 예를 들어 데이터 공급 계약이 진행 중이면 앱 화면과 관리자 기본 편집기는 샘플 데이터로 진행할 수 있다. 다만 실제 공급 검증을 마친 것으로 표시하거나 샘플을 운영 가격·뉴스로 게시하지 않는다.

3단계의 외부 공급 검증은 병행 트랙이다. 4~6단계 M1은 카탈로그·명시된 수동/샘플 fixtures로 진행할 수 있다. 공급 대기 중 M1까지 막지 않으며 허용 실데이터가 없는 7/8단계의 샘플 구현은 실제 공급 통과와 구분한다.

## 4. Git 저장소와 브랜치 운영

### 저장소 초기 작업

1. 새 프로젝트 폴더에서만 Git 저장소를 초기화한다.
2. `main`을 기본 브랜치로 정하고 README·기획 기준·환경 예시·제외 목록을 먼저 기록한다.
3. GitHub 비공개 저장소를 기본안으로 연결한다. 원격 저장소 생성·인증은 실제 착수 단계에서 처리한다.
4. 비밀키·실제 환경 파일·앱 서명 파일·사용자 데이터·계약 원문이 커밋에 들어가지 않게 한다.
5. main 반영 전 자동 검사와 변경 검토를 적용하고, 배포한 커밋을 태그로 식별한다.

## 7. 3단계 — 뉴스·원문·시세 공급 검증

부록106행은 원본 보존 대상이지 독립 매체 수나 모두 가동 중이라는 뜻이 아니다. 권한 미확인은 RIGHTS_HOLD로 표시한다. CANDIDATE는 등록 직후 평가 전 임시 상태이며 요청 실행 불가다. 첫 평가에서 이용 범위 미확인은 RIGHTS_HOLD로 전환한다. 부록의 미확인 초기값은 RIGHTS_HOLD / RIGHTS_UNVERIFIED로 통일한다.

시트 외 경로도 같은 sources/permission_profiles/endpoint/adapter 버전에 등록한다. 네이버·Brave는 검토 중인 발견 전용 검색 API이며 PLATFORM_RESOLVE·쿼리 예산 큐다. 자체 독립 근거로 세지 않는다. DART/KIND/SEC/중앙은행/정부/기업IR 등은 OFFICIAL 원문·정정 감시 경로다. 계약·기술·허용량 미확정은 비활성으로 둔다. 공식성만으로 수집·보관 허가를 추정하지 않는다.

감시 주제의 검색 표현·별칭·우선순위 수정과 기존 ACTIVE 경로 선택은 다음 회차 반영한다. 새 URL은 등록 요청이며 권한→기술→SHADOW→ACTIVE 검증을 건너뛰지 않는다. 일시 가용성 복구와 신규/품질 강등 SHADOW는 상세로직의 서로 다른 복구 절차를 적용한다.

산출물: 허용범위·권한프로필·공급계약/예산·URL/endpoint·adapter버전·주기·origin규칙·회복검사·수집/시세 공급시험 기록. 실제 구성 종목 거래소(KRX·NYSE·Nasdaq 등)의 휴장/조기종료 공식 자료원·timezone·갱신 주기·실패 시 마지막 검증 버전과 미확보 표지, 평가 라벨 기준과 허용된 최초 사례를 포함한다. 실제 미확정 경로는 비활성. 완료기준 A34~38,A43,A48,A52~54,U06. 검색 API 사용 여부는 시험 후 구성으로 고정한다.

제작 전체0~12단계가 순서를 정한다. 상세로직의7단계는 작업영역 분해이며 별도 일정을 뜻하지 않는다. 대응: 상세1→제작4·5,2→3·8,3→8·9,4→5·9,5→7,6→10·11,7→12. 수동 M1은 자동 운영 전 검증 흐름이며 출시 후 모든 기사에 운영자를 요구하는 설계가 아니다.

공개 상태는 DRAFT/PUBLISHED/CORRECTION_PENDING/WITHDRAWN/HIDDEN. 예약은 DRAFT + scheduled_publish_at이며 예약시각에도 최신 근거·정책·catalog_version을 재검사한다. 수동 작성의 선택적 REVIEW 플래그는 공개 상태가 아니다. 자동 후보 판정은 COLLECT/PASS/HOLD/EXPIRED_HOLD와 상세로직 사유 체계를 사용한다. 수집 성공/부분 실패·수집처 상태도 별도 축이다.

일상 섹터·매크로 게시와 보류 재판정은 무인 처리한다. 관리자 검수 대기라는 말은 모든 기사에 사람 승인을 강제하는 뜻으로 쓰지 않는다. HOLD는 사유·깨울 조건·판정횟수·원래 deadline을 가진다. 새 근거 없이 반복 호출하지 않고, 상세로직의 24/72시간 상한을 지킨다. 수동 보호 글의 AI 수정은 제안으로 남기되 잘못된 본문의 안전 차단은 즉시 한다.

최신 문서 기준은56카테고리·에이직랜드 제외 한국기업339개이며 실제 시트 재조회 결과라는 뜻은 아니다. 구판의340개는 그 시점 스냅샷 이력이다. import는 실제 최신 시트·원본 좌표·해시·차이·수동충돌을 확인한 뒤 적용한다. 초기 이관 후 운영 DB가 기준이며 시트와 양방향 자동 덮어쓰기는 하지 않는다.

섹터명·설명·순서·삭제(비활성), 하위 묶음·한국종목 추가/해제/순서, 기업 마스터 비활성·대체, 내부 제품 역할·미국 비교군 버전을 관리한다. 관련 메타데이터가 바뀌면 catalog_version 증가, 영향 미리보기·원자 적용·감사 기록. old job은 커밋 직전 최신 버전으로 재검사한다. 삭제 기업/섹터를 재연결하지 않는다. 표시 설명E·묶음 설명·내부 상세 역할은 분리한다. 대표 섹터 대체는 본문 실질 변화가 없으면 메타데이터 버전만 올리고 최초/본문 수정일을 바꾸지 않는다.

DB migration에는 scheduled_publish_at, policies/catalog_versions, permission_profiles, sources/endpoints/adapters/checkpoints, source_documents/revisions, stories/issues, claims/evidence_edges, article_versions/impacts, decisions/holds, ranking_snapshots/entries, outbox/notification_deliveries, private view_events/aggregates, keyword_changes/audits, purge/tombstone을 포함한다. 공개 목록·본문과 알려진ID resolver를 분리한다. 키/권한·설치소유권·서비스전용 쓰기·로컬 migration 재생과 하위 호환 시험 후 앱을 연결한다. 운영은expand/contract·roll-forward 우선이며 코드 롤백과 데이터 복원은 별도 절차다. 운영 데이터를 지우는 down migration을 일반 복귀 수단으로 쓰지 않는다.

### 4단계 공통 작업 기반 — 5단계 시작 전 필수

DB 게시 트랜잭션에서 article_version·공개 포인터·impact·outbox를 함께 쓴다. 공통 worker는 jobs/outbox의 작업키·effect_key unique·lease/visibility timeout·인수/완료/재시도/DLQ를 구현한다. 외부 호출은 DB 잠금 밖이다. 이 단계는 공용 실행기와 모의 효과까지만이며 수집·AI 전체를 앞당기는 뜻이 아니다.

P01: 같은 게시 이벤트 두 번·프로세스 종료 후 재인수·lease 만료·이중 consumer·부분 효과 성공을 재현한다. DB 내부 효과는 unique/CAS로 한 번 반영하고 외부 전송은 기존 멱등키를 유지한다. 공급처 수락 불확실을 새키 재발송으로 풀지 않는다. 작업을 잃거나 완료 전 ACK하지 않는다. 장시간 작업의 heartbeat/lease 연장·최대시도·DLQ·권한 있는 재처리를 고정한다. Cron은 예약키로 큐 등록만 하고 worker가 처리한다. 동일 예약을 양쪽에서 만들지 않는다. P02는 Cron→큐→consumer까지 검증하며 실제 유료 공급·실제 푸시는 모의 효과로 대체한다.

contracts에 selection_market_basis/source_market/analysis_perspective/impact_profile/visibility_policy_version·서버 visible_sections 형식을4단계에 두고,5단계에서 한국 관점의 수동 입력·근거별 영향 분류·관리자/앱 동일 노출을 구현한다.4단계 완료는 P01 전체·P02a(Cron→큐→worker 모의효과)·P03a(계약필드·서버 노출 판정 단위시험)·P04a(clock/calendar 인터페이스·고정시계 시험)와 migration/권한 검사를 요구한다. 실제 관리자/앱 구현을 요구하는 P02b/P03b는5~6단계 M1, 실공급·시장/달력 통합 P04b는7단계 M2에서 완료한다. M0에는 이 후속 증거를 요구하지 않으며 각 부분 증거의 단계·시험자료·실행 결과를 따로 기록한다.

## 9. 5~6단계 — 수동 운영 가능한 프론트 완성

### 5단계: 가장 먼저 완성할 전체 흐름

```text
관리자 로그인
→ 기사 작성·대표 섹터 선택·미리보기
→ 게시
→ Supabase 공개 조회
→ Android·iOS 홈 배지·필터·섹터체크 목록·상세
→ 관리자 수정·숨김
→ 앱·검색 공개 결과에 반영
```

이 흐름이 첫 핵심 완료 지점이다. 4단계 공통 큐/outbox 통과가 선행하며 R05~R08을 수동 fixtures로 검증한다. 긍정만/긍정·부정/피해만/연관 조건부·미래 일정의 서버 판정과 관리자 미리보기·양쪽 앱 노출이 일치해야 한다. AI가 없어도 수동으로 운영 가능한 구조를 먼저 만든다. 기사 버전·발행 시각·수동 수정 보호·숨김 상태를 처음부터 적용한다. 수동·AI 기사가 공유하는 편집기에 활성 섹터 선택을 배치한다. 섹터 기사의 대표 섹터는 예약·게시 전에 채운다. 매크로 기사는 근거가 있는 관련 섹터를 연결하고, 시장 전반 이슈의 대표 섹터는 비워 둘 수 있다. 연결이 여러 개여도 같은 이슈가 중복 노출되지 않게 한다.

### 신규 기능 구현 순서

1. **섹터 설정과 앱 연결.** 상위 탭·하위 섹터의 이름·설명글·순서를 편집하고 저장한다. 설명글 최초값은 기준 시트 상단 C열을 사용하고 섹터체크의 섹터명 아래에 표시한다. 섹터 삭제는 연결 대상을 미리 보여준 뒤 비활성화로 처리한다. 게시·예약 글이 해당 섹터를 대표로 사용하면 대체 섹터를 지정하고, 상위 섹터의 활성 하위 섹터는 이동 또는 비활성화 대상을 먼저 정한다. 공개 목록과 필터의 섹터 데이터가 바뀌면 갱신하고, 기존 선택은 활성 ID 기준으로 정리한다. 초기 상위 분류 연결은 서비스 기획안의 ‘초기 섹터 분류’를 사용한다. 합의 11의 하위 카테고리와 기업은 고정 ID로 연결하고, HTML 카탈로그와 앱 필터의 분류가 다르면 이관 전에 확인한다. 엔터의 상위 그룹이 통신 · 엔터 · 게임인지 확인한다. ‘소비재 전체’에서는 엔터가 제외되고 ‘통신 · 엔터 · 게임 전체’에는 통신·엔터·게임이 모두 포함되는지 검증한다. 섹터 이름 변경 후에도 기사·기존 선택이 이어지는지 검증한다.
2. **섹터 상세와 종목 연결.** 하위 카테고리의 이름과 순서, 한국 종목의 연결과 묶음별 설명을 편집한다. 종목 추가·삭제·순서 변경과 묶음 이동을 지원한다. 같은 회사가 다른 묶음에 속하면 각 설명을 사용한다. 과거 섹터 성과는 당시 구성 기준을 보존한다.
3. **종목 웹뷰.** 섹터체크의 관련 종목 행에서 검증된 코드로 네이버증권 모바일 종합 주소를 구성한다. Expo 웹뷰에서 열고 로딩·실패·외부 브라우저 대체·뒤로가기를 Android·iOS에서 검증한다. [Expo 웹뷰](https://docs.expo.dev/versions/latest/sdk/webview/) [네이버증권 삼성전자 종합](https://m.stock.naver.com/domestic/stock/005930/total)
4. **저장·알림 경로.** 하단 네 번째 탭을 저장으로 구성한다. 홈·이슈체크 카드와 공통 상세에서 기사 ID 기준으로 저장·취소한다. 기기 저장소에 ID와 시각을 유지하고, 저장 화면은 최근 저장 순서로 제공하며 숨김/철회는 본문 없는 안내 항목을 유지한다. resolver 정규 ID로 앱이 로컬 저장을 치환·중복 제거한다. 저장 화면 상단 알림 아이콘 → 기존 알림 → 설정과 되돌아오기를 연결한다. ## 10. 7단계 — 시세·섹터 성과·랭킹

여섯 날짜 버튼 오늘·어제·이번주·지난주·이번달·지난달의 뜻은 한국 달력과 **최초 앱 게시일**이다. 오늘/어제는 단일 날짜 표시를 유지한다. 업데이트로 최초 게시일을 바꾸지 않는다.

최초 진입 홈은 **실시간** 상태이며 날짜 버튼은 미선택이다. 일곱 번째 기간 탭은 추가하지 않는다. 콘텐츠 위 상태줄에 ‘실시간 · 실제 시작~종료 · 거래일 기준’을 표시한다. 버튼을 고르면 달력 보기로 전환하고, ‘실시간으로’ 링크로 기본 상태로 돌아온다. 달력 오늘과 거래 구간을 같은 선택값으로 부르지 않는다.

실시간 C는 한국 시각 **09:10 이상~20:00 미만 KR**, **20:00 이상~다음09:10 미만 FOREIGN_US**로 전환한다. 한국 비거래일에는 KR을 만들지 않고 FOREIGN_US를 유지한다. 20:00은 해외 기준 첫 회차이며 한국 기준 마지막 회차는19:50이다. 한국 기준은 거래일 D, 직전 한국 정규장 종료 직후~회차 cutoff를 후보 창으로 고정한다. 해외 기준은 다음 한국 거래일 D, 직전 한국 정규장 종료 직후~회차 cutoff를 사용한다. 금요일 장후·주말·연휴를 빠뜨리지 않는다. 09:10 전환 때 D·하한을 유지하며 market_basis만 바꾼다. 20:00 전환 때 다음 D로 이동한다. 최초 게시일·Story/Issue ID는 바꾸지 않는다. A/B의 이전 글은 현재 실질 변화가 있을 때 최초 날짜+업데이트 일시를 표시한다. 뉴스 게시와 별개로 C만10분 스냅샷이다. 전환 실패는 현재 모드의 지연/미확보로 표시하고 다른 시장의 직전 순위를 현재 순위로 재사용하지 않는다. 구모드 결과는 기준시각·시장명을 붙인 별도 과거 참조로만 제공한다.

## 11. 8~9단계 — 뉴스·AI 봇 제작

부록106행은 원본 보존 대상이지 독립 매체 수나 모두 가동 중이라는 뜻이 아니다. 권한 미확인은 RIGHTS_HOLD로 표시한다. CANDIDATE는 등록 직후 평가 전 임시 상태이며 요청 실행 불가다. 첫 평가에서 이용 범위 미확인은 RIGHTS_HOLD로 전환한다. 부록의 미확인 초기값은 RIGHTS_HOLD / RIGHTS_UNVERIFIED로 통일한다.

시트 외 경로도 같은 sources/permission_profiles/endpoint/adapter 버전에 등록한다. 네이버·Brave는 검토 중인 발견 전용 검색 API이며 PLATFORM_RESOLVE·쿼리 예산 큐다. 자체 독립 근거로 세지 않는다. DART/KIND/SEC/중앙은행/정부/기업IR 등은 OFFICIAL 원문·정정 감시 경로다. 계약·기술·허용량 미확정은 비활성으로 둔다. 공식성만으로 수집·보관 허가를 추정하지 않는다.

감시 주제의 검색 표현·별칭·우선순위 수정과 기존 ACTIVE 경로 선택은 다음 회차 반영한다. 새 URL은 등록 요청이며 권한→기술→SHADOW→ACTIVE 검증을 건너뛰지 않는다. 일시 가용성 복구와 신규/품질 강등 SHADOW는 상세로직의 서로 다른 복구 절차를 적용한다.

SourceDocument는 원문, Story는 실제 사건, Issue는 앱 상세의 방향이다. Story 1:N Issue, Issue 1:N article_version. 새 사실·새 영향 경로와 독립 제목의 실질·기존 상세로 처리 불충분·기존 방향 전수 비교를 모두 통과한 경우만 NEW_ANGLE로 별도 Issue를 만든다. 일반 후속은 UPDATE 우선. 표현·주가 반응만 바뀌면 새 글을 만들지 않는다.

조회·저장은 Issue 단위이며 부모의 조회를 새 방향에 복사하지 않는다. 홈은 A→B→C 전체에서 Story당 한 카드다. 대표 Issue는 공개·자격 통과 후보 중 A 자격 우선, 다음 B 자격, 다음 기존 대표가 자격을 유지하면 유지한다. 새 실질 변화로 상위 lane 자격이 생길 때만 교체한다. 동률은 최근 material_change_at, 최초 published_at, 고정 Issue ID 순이다. C의 조회 점수 변동만으로 대표를 바꾸지 않는다. 다른 방향은 상세 후속 링크·이슈체크·검색에서 제공한다.

핵심 주장에 ORDINARY_FACT/SYSTEMIC_MACRO/SENSITIVE_UNCONFIRMED를 부여한다. SYSTEMIC_MACRO는 일반/주요 또는 SECTOR라는 기사명과 관계없이 공식 원문 1개 또는 독립 원출처 3개, 한국 전달 경로, 사실의 유효성을 확인해야 한다. 부족하면 A/B/C·일반 목록 모두 게시 보류다. 관리자 수동 게시에도 같은 게이트를 적용하며 우회 게시 권한은 두지 않는다.

공식 확인은 해당 기관이 확인한 사실 범위만 충족한다. 정책 발표 1개로 모든 기업 수혜를 확정하지 않는다. 같은 통신사·보도자료·동일 취재 재인용은 1건, 같은 소유 그룹은 보수적으로 최대 1건이다. 원출처/그룹 미확정은 독립3에 더하지 않는다. 카테고리 소속은 기업 직접 영향 근거가 아니다. 주요 A 승격은 위 기준에 중요도·현재 한국 시장 영향을 추가한다.

병합 전 양쪽 Story의 거시/기업 분류와 필요한 entity 집합을 읽어 잠금 계획을 만든다. MACRO_ALL(해당/분류 불확실 시)→정렬 entity ID→정렬 Story ID 순으로만 진입한다. 잠금 후 다른 파티션/기업 잠금이 필요함을 알게 되면 전부 풀고 계획을 다시 만들어 처음부터 순서대로 재진입한다. 이미 Story 잠금을 잡은 상태에서 상위 파티션 잠금을 추가하지 않는다.

잠금 안에서는 최신 catalog/policy·canonical key·사실 집합을 재조회하는 짧은 결정/커밋만 한다. DB lock_timeout 초기2초·transaction5초, 실패 시 HOLD(H_CONCURRENCY) 후 재시도한다. 원문/LLM 네트워크 호출을 잠금 안에 두지 않는다. 불확실하면 초안을 저장하고 잠금을 풀어 재분석 후 expected_version 검사로 재진입한다. 외부 결정 ID unique와 정규 사건/Issue 방향 unique·outbox 효과키가 함께 중복을 막는다. 실제 처리량·교착은 구현 시험으로 검증한다.

원문 접근·AI 분석 권한이 확인된 리포트는 SECTOR의 **분석/추정 의견** 기사 근거가 될 수 있다. 기존 공개 사실과 리포트의 새 추정·가정·의견을 분리하고 상세 핵심 이슈 위에 ‘리포트 의견’, 작성 증권사·원문 시각·원문 링크를 표시한다. 검증 가능한 공개 사실과 계산/추정 근거가 없는 목표가 홍보는 제외한다. 리포트1건으로 SYSTEMIC_MACRO 사실·미확정 계약·확정 수혜를 게시하지 않는다. 인용 허용 범위 밖 표/문장 복제 금지. 권한 미확정 리포트/Telegram은 RIGHTS_HOLD 유지다.

8단계는 허용 소수 경로의 목록/원문·증분·부분실패·보관·관측/경보와 평가 세트 동결(P05~06)을 검증한다.9단계는 사실/영향/작성·별도검사·원자게시/outbox·정정/수동보호를 검증 환경 SHADOW에서 연결하고 고정 평가 세트로 판정한다(P07). SHADOW 결과는 운영 공개·실제 푸시가 없다. 격리된 검증 환경의 자동 게시 모의시험은 허용한다. 운영 LIVE 활성화는12단계 공통 게이트 통과 범위로만 한다. A01~19,A33~46,A53,A55,U01,U05~06,U09,U14~15,R05~08 및 R02~04/R09의 단계별 부분 시험을 기록하고10단계에서 통합한다.

## 12. 10단계 — 스케줄·20:00 정비

4단계에서 검증한 공통 실행기를 사용한다.10단계는 큐를 처음 만드는 단계가 아니라 전체24시간 운영·복구·부하 통합 검증이다. Supabase Cron은 예약·큐 등록, Docker worker는 처리. 같은 예약을 양쪽에서 중복 생성하지 않는다. 홈 스냅샷은24시간 매10분이며 한국 거래일09:10~19:50 KR65회,20:00~다음09:00 FOREIGN_US79회다. 한국 휴일은FOREIGN_US로 계속한다. 뉴스 단계별 큐는 준비 이벤트로24시간 실행하며 홈 예약을 기다리지 않는다.

매 달력일20:00 실행한다. 범위 변화 없는 기존 검색어의 약어·표기 변형만 공식 용어 또는 독립 원출처3건·표본 검증 후 자동 별칭 연결한다. 기존 카테고리의 신규 의미 연결·새 기업/제품 역할·수혜 판정·카테고리 통합/삭제·새 출처 활성화는 자동 반영하지 않고 근거 있는 제안으로 보존한다. 예외가 대기해도 기존 조건으로 계속 운영한다. 하단D 앱 검색어·E 표시 설명·F 보조문맥은 뉴스 키워드 정비가 자동 변경하지 않는다.

키워드 정비 D일 묶음은 **전날20:00 초과~D일20:00 이하**의 연속24시간 창이다. 앱 게시일·한국장65회와 구분한다. 각 원문판본의 keyword_eligible_at은 max(최초 발견 작업의 예약시각, 확인된 원문 발표시각)으로 한 번 고정한다. 20:00 회차가 20:01 발표를 뒤늦게 받아도 다음날 묶음이고,19:50 작업이20:03에 끝나도 발표가19:50 이전이면 D일 묶음이다. 22:00 발표를22:10 수집하면 다음날20:00 묶음에 포함한다.20:01·23:59·00:00 자료도 빠짐없이 각각 한 번 포함한다. 발행시각 미확인은 PENDING_TIME으로 두고 확인 후 이 규칙에 따라 귀속하며 원래 날짜의 늦은 추가 묶음이 될 수 있다.

PENDING_TIME은 최초 발견 후72시간 상한이다. 그 안에 확인되면 위 규칙, 끝내 미확인이면 최초 발견 작업의 예약시각을 keyword_eligible_at으로 고정하고 ‘시각 미확인 · 발견 기준’ 표지를 남겨 그 귀속 날짜의 늦은 추가 묶음으로 처리한다. 확정한 귀속은 뒤늦은 원문 시각 발견으로 재이동·중복 반영하지 않고 정정 이력만 추가한다. 이는 키워드 정비 자료의 귀속 규칙일 뿐이며 기사 게시의 신선도/근거/HOLD 기준을 완화하지 않는다.

작업ID 목록과 SourceDocument/revision별 고정 귀속을 cutoff manifest로 보존한다. 한 폴링 작업이 경계를 넘는 판본을 받으면 판본별로 서로 다른 묶음에 배정할 수 있다. 이미 콘텐츠 판단 이벤트에서 처리한 자료도 같은 판본 ID로 한 번만 센다.20:30 미완료는 PARTIAL로 마감하고 뒤늦은 결과는 고정 귀속 날짜의 추가 묶음으로 처리한다. 신규자료를 임의로 과거 날짜에 넣거나 같은 판본을 다음날 재반영하지 않는다. 기준버전 충돌·재실행·부분 선적용·관찰·개별관계 롤백을 기록한다.

유효 조회 원시30일·일별 집계1년은 개인정보 확인 전 초기 상한이다. UV는 요청 구간 전체가 원시 보관 창 안에 있고 집계가 정상인 경우에만 계산한다. 30일 밖의 주/월/임의기간 UV는 초기 기능에서 **지원하지 않음**으로 표시한다. 31일짜리 달의 정확 월 UV도 제공하지 않는다. 원시 이벤트 만료 전 장기 집계를 만들었다고 추정하지 않는다. PV 합계와 일별 UV 각각은 제공할 수 있으나 일별 UV 합을 기간 UV라고 표시하지 않는다. 설치 목록·기간별 고유집합을 장기 보존하는 우회 집계는 도입하지 않는다. 보관 창 안에서도 원시 누락/배치 실패가 있으면 ‘집계 미확보’다.

원시 보관은 서버 수락시각 기준 **30×24시간 롤링**이며 삭제 작업은 그보다 오래된 이벤트만 대상으로 한다. UV 질의는 고정 as_of와 동일 DB 읽기 스냅샷에서 완전성 watermark를 확인한다. 초기 안전 여유1시간을 두고 start≥as_of−(30×24시간−1시간), end≤as_of이며 실제 보관/집계 watermark도 요청 시작을 덮어야 지원한다. 한국 달력 구간을 UTC 경계로 변환해 이 조건을 검사한다. 30일짜리 달도 월말이라는 이유로 자동 지원하지 않는다. 여유 안에서도 수집/집계 누락이 있으면 집계 미확보로 표시하고 일별합으로 대체하지 않는다.

원문 허용기간 만료·권한 철회는 source_revision·blob·임베딩·검색색인·LLM cache·파생 결과·백업 복구 경로까지 삭제/비공개 정책으로 연결한다. 최소 식별 tombstone은 허용된 범위에서만 남겨 재수집·재게시를 막는다. 삭제 ledger는 복원 후에도 재적용한다. 삭제 완료와 백업에서 완전 소거 시점을 구분하고 권한 철회 건은 복원 직후 공개 전에 차단한다. 실제 보관기간·데이터 항목은 개인정보 문서와 일치해야 한다.

A10~11,A28~31,A37,A44,A51,A54~55,U11~13,R02~R04,R09,P06~07,P09~10을2단계 고정 시계·3단계 캘린더 및 실제 검증 예약 양쪽에서 확인한다. 정정/철회 차단·프로세스 재시작·자정/휴일·09:10/20:00·PENDING_TIME을 포함한다. 지연/품질/비용 기준은 아래18절 품질 계약으로8단계까지 동결하며 미확정이면 LIVE 불가다. 전체집계 실패를 조회0이나 새시세로 저장하지 않는다.

## 14. 환경·Docker·비밀키·배포의 분리

### 환경 구성

| 환경 | DB | 앱·웹·봇 | 목적 |
| --- | --- | --- | --- |
| 로컬 | Docker 기반 로컬 Supabase | 개발 실행·샘플·시험 공급처 | 구현·실패 사례 시험 |
| 검증 | 검증용 Supabase 프로젝트 | preview 빌드·검증 관리자·검증 worker | 실기기·실제 예약·이관·배포 확인 |
| 운영 | 운영용 Supabase 프로젝트 | production 빌드·운영 관리자·운영 worker | 실제 이용자 서비스 |

초기에는 로컬만으로 시작할 수 있다. 실제 운영 연결 전 검증·운영 DB/worker/키/푸시 대상의 분리를 필수 게이트로 확인한다. 별도 Supabase 프로젝트를 기본안으로 하며 브랜치 대체는 동등 격리·credential 범위를 증명한 경우에만 채택한다. 생성·요금·권한은 착수 시 확인한다. DB 브랜칭 기능 사용 여부와 Git 브랜치는 구분한다.

### Docker 사용 범위

- 개발자 PC: 로컬 Supabase를 실행하는 컨테이너 환경.
- 개발자 PC: 필요하면 Compose로 news-worker 실행과 환경 전달을 재현.
- 운영: news-worker 이미지를 작업 실행 서비스에 배포.
- Expo 앱: Docker로 휴대폰 앱을 실행하는 구성이 아니다. Expo 빌드 경로를 사용한다.
- 운영 DB: Supabase 관리형 DB를 기본으로 하며 Docker DB를 추가 운영하지 않는다.

### 비밀키 위치

앱의 공개 환경 변수와 서버 비밀값을 구분한다. `EXPO_PUBLIC_` 설정에는 서버 비밀키를 넣지 않는다. 관리자 서비스 권한, 뉴스·AI·시세 키, DB 자격정보는 해당 서버·worker의 비밀 설정에서만 사용한다.

`.env.example`에는 이름·설명·빈 예시만 두고 실제 값은 커밋하지 않는다. 저장소·빌드 로그·에러 메시지에 키가 노출되지 않게 한다. 시세·AI 공급처의 검증·운영 키 또는 사용량 구분도 가능 범위에서 분리한다.

### 운영 배치안

관리형 Supabase 한 운영 프로젝트, 관리자 웹 배포 한 곳, Docker worker 배포 한 곳, Expo 앱 빌드·스토어 배포 경로가 기본 구성이다. Android·iOS가 각각 다른 백엔드를 쓰지 않는다. 관리자 호스팅과 worker 호스팅은 계정·배포 대상이지 물리 서버 한 대씩을 직접 구매해야 한다는 뜻이 아니다.

### 평가 자료와 품질 합격 기준 {#evaluation-gate}

3단계에서 사건/원문판본·동일사건/NEW_ANGLE/UPDATE·홍보/범위·SYSTEMIC_MACRO 게이트·한국 영향·impact_profile/visible_sections 라벨 기준을 만든다. 이용 범위가 확인된 경로부터3~8단계에 사례를 축적하고8단계 끝에 개발용/고정 검증용을 Story·기간 기준으로 분리해 동결한다. 프롬프트 조정에 쓴 사건을 같은 고정 검증 분모에 몰래 섞지 않는다. 초기 라벨 작성·분쟁 해소는 개발 검증이며 출시 후 상시 수동 기사 승인을 뜻하지 않는다.

평가 registry는 원문 ID·revision hash·사건 ID·허용 발췌/근거 좌표·정답 라벨·작성/검증 근거·permission_profile·expires_at·dataset_version·분할을 보관한다. 원문/PDF는 기존 최대30일 또는 계약의 더 짧은 한도를 지킨다. ID·라벨·발췌도 허용된 범위만 남긴다. 평가용이라는 이유로 원문·임베딩·캐시 보관 예외를 자동 만들지 않는다. 원문 만료/철회 시 연결된 발췌·파생 자료도 정책대로 삭제/비공개하고 평가 적격성을 다시 계산한다. 재현 가능한 자료가 부족하면 대체 허용 자료로 새 dataset_version을 검증해 동결한다. 이전 버전의 해시/판정 기록은 허용 범위의 메타데이터만 보존하며 없어진 원문을 복원하지 않는다.

운영 연결 전 app build profile/channel/runtime·API URL·Supabase project_ref·관리자/worker deployment_id·DB/queue target·정책/카탈로그·secret namespace·푸시 project 자격·테스트/실광고 ID를 하나의 release_manifest로 대조한다. 로그에는 키 자체를 남기지 않는다. 검증/운영 credential·데이터 쓰기와 발송 대상은 격리하고 worker 시작 시 실제 연결 환경을 검증한다. 지정 환경이 다르면 쓰기/발송 전 실패한다. 검증 JWT/설치 권한으로 운영 쓰기 거부, 서비스 키 없는 공개 클라이언트의 관리자 쓰기 거부, 검증 예약/푸시가 운영 대상으로 확장되지 않음을 시험한다. 공개 anon key·빌드 설정 문자열만 보안 경계라고 주장하지 않는다. 변조 클라이언트 일반을 설정값으로 완전히 차단한다고 약속하지 않고 서버 소유권/RLS·발송 자격을 강제한다.

### 배포·이전 앱·복구 {#deployment-contract}

4단계에서 공개 API 계약과 최소 지원 앱 버전을 정의하고 첫 앱부터 버전 확인·‘업데이트 필요’ 응답/화면·스토어 이동·통신 실패 안내를 구현한다. 신규 필드는 이전 앱에 호환되게 추가한다. 배포는 `expand migration → 하위 호환 서버/API/worker → Android/iOS 빌드 또는 호환 JS 업데이트 → 구버전 사용/지원 정책 확인 → contract migration`이다. 실제 앱은 강제 회수가 불가능하므로 지원 종료 조건·최소 버전 적용 근거 없이 기존 필드/endpoint를 제거하지 않는다. 작업 payload도 job_schema_version으로 관리해 이전 worker가 처리할 수 없는 새 형식은 배포 순서/consumer fencing으로 보호한다. 활성 lease 처리·drain/재인수·이중 effect를 배포 리허설에 포함한다.

Expo 초기 runtimeVersion 정책은 플랫폼별 네이티브 릴리스 ID를 명시 관리하는 방식으로 고정한다. 네이티브 SDK·config plugin·native 설정을 바꾸면 새 runtimeVersion과 새 바이너리를 만들고 내부 배포에서 확인한다. CI에 native 입력 digest/런타임 변경 점검을 둔다. JS 업데이트는 같은 네이티브 runtime과 서버 계약에 호환되는 경우만 해당 channel로 보낸다. 빌드 버전·스토어 build number·runtimeVersion·API 최소 지원 버전을 서로 같은 값으로 오인하지 않는다. [Expo 런타임 호환 기준](https://docs.expo.dev/eas-update/runtime-versions/)

코드 롤백은 호환되는 이전 앱 업데이트/웹/worker의 재배포이며 운영 데이터 전체를 과거로 되돌리지 않는다. DB는 원칙적으로 roll-forward 수정이다. 데이터 복원은 장애 범위·백업 시각·RPO/RTO·복원 후 소실 가능 쓰기/외부 효과를 확인하는 별도 절차다. 복원은 격리 환경에서 무결성·삭제 ledger/tombstone·숨김/철회·outbox/delivery·권한을 재적용한 뒤 공개를 열고 이미 보낸 푸시를 재전송하지 않는다. 개인정보·원문 삭제가 복원으로 취소되지 않게 한다. 일반 재시작 복구와 재해 복원을 구분한다.

**확정 요구:** 뉴스 수집·분석·신규 게시·기존 글 업데이트·정정/철회는 주말·휴일을 포함해24시간 계속한다. 뉴스 한 건은 `발견 → 중복/홍보/범위 판별 → 허용된 본문·공식 근거 확인 → 사실/한국 영향 분석 → Story/Issue 비교 → 신규 작성 또는 기존 버전 수정 → 게시 검사 → 원자 공개·캐시/검색 반영` 순서로 처리한다. 게시 기준을 통과하면 다음10분 순위 회차·20시 키워드 작업·다음 장전까지 기다리지 않고 반영한다. HOLD·예약·수동 보호·권한 미확인은 기존 제한을 그대로 적용한다. 원문만 들어왔다고 즉시 무조건 게시하는 뜻은 아니다.

**구현 계약:** 단계별 영속 큐·작업키·lease·재시도·실패 큐를 두고 서로 다른 사건은 제한된 동시성으로 처리한다. 같은 사건/Issue의 결정과 수정은 공통계약15절 잠금·expected_version·unique키로 직렬화한다. 한 기사 분석이 오래 걸려도 새 목록 수집과 다른 사건 처리는 계속된다. 원문/LLM 호출은 DB 잠금 밖에서 수행한다. ‘순차’는 기사 내부의 단계 의존성이지 전체 시스템 단일 직렬 실행이 아니다. 수집 빈도는 뉴스 상세로직4절의 허용 경로별 주기이고, 수집 후 단계는 준비 이벤트에 따라 실행한다. 새 근거가 없는HOLD를 매 순간 재분석하지 않는다. worker/LLM 비용·공급처 호출 제한도 계속 지킨다.

**홈과의 분리:** 공개 즉시 상세·이슈체크·검색·저장 resolver에 최신 공개 버전을 반영한다. A/B는 게시/중요변화 이벤트로 자격을 검사해 반영하고10분 만료 감시는 보조다. C 점수·순서 재계산은24시간10분 스냅샷 작업이다. 미게시/비공개 본문은 노출하지 않으며 정정·숨김·철회는 다음 스냅샷을 기다리지 않고 현재 홈의 해당 카드·본문·캐시를 즉시 차단한다. 과거 스냅샷 원본은 감사용으로 보존하되 공개 조회 시 현재 상태 필터를 적용한다. C 순위 실패가 기사 게시를 막거나 새 기사를 유실시키지 않는다. 새 글은 C 반영 전에도 목록/검색과 적격A/B에서 제공한다.

20:00 키워드 정비와 뉴스 큐는 독립 실행한다. 정비 작업이 원문 발견·분석·게시·정정 큐를 중지하거나 같은 잠금을 장시간 독점하지 않게 자원을 분리한다. 푸시는 게시와 별도이며 기존 동의·야간·빈도·원인 중복 제한을 유지한다. 지연/실패는 단계별 상태·최초 발견/분석/게시 시각으로 관측한다. 실운영 지연시간은 공급·용량시험 전 보장하지 않는다.

가격 장애 대체 조회의 `snapshot_context_id`는 market_basis·target_D·candidate_window_start(후보창 하한)·정렬모드·ranking_policy_version·catalog_version·benchmark_version·price_session_id의 고정 조합으로 정의한다. 후보창 상한인 회차cutoff는 이 동일성 키에서 제외한다. 같은context의10:00 정상 결과를10:10 장애 때 실제10:00 기준시각·지연 표시와 함께 유지할 수 있다. 대체 스냅샷cutoff는 요청cutoff 이하여야 하며 현재 공개 상태 필터는 다시 적용한다.20:00 KR→FOREIGN_US,09:10 FOREIGN_US→KR 또는D/하한/정책/비교군/세션이 달라지면 context가 다르므로 대체하지 않는다. 같은context의 이전 결과가 없으면 해당모드 순위 미확보다. 순위 공개 포인터는 요청한context와현재rank_epoch를CAS로검사해 늦은구모드작업이 현재모드를 덮지 못하게 한다.

달력 구간의 마지막cutoff 이후부터 구간 종료 직전까지 최초 게시된 글(예:09:05·19:55·23:55)은 해당 구간 스냅샷에 들어가지 못하므로 의도적으로 ‘당시 순위 미포함’에 보존한다. 다음 구간의 실시간C에는 자격에 따라 포함될 수 있으나 그 순위를 이전 달력 구간으로 소급 복사하지 않는다. 기사 게시 자체는 즉시 반영되며 역사 순위가 없다는 이유로 글을 숨기거나 새 구간의 최초 게시일로 이동하지 않는다.

### 뉴스 선정 시장과 한국 주식 분석 관점 {#korean-perspective}

**확정 요구:** 한국 시각09:10 이상~20:00 미만에는 한국 주가·섹터 신호,20:00 이상~다음09:10 미만에는 해외 주가·기업·매크로 신호를 뉴스 탐색·홈M의 우선 기준으로 사용한다. 한국 휴일에는 해외 기준을 유지한다. 시간대는 검색 우선순위·시장 지표를 바꾸며 다른 국가의 중요한 공시·한국 관련 매크로·악재 수집을 차단하지 않는다. 가격 상승은 게시 필수조건이 아니다.

핵심 이슈는 해당 사건 주체·시각·실적·정책 등 **원래 사건의 사실**을 쓴다. 해외 선정 기사라면 해외 기업/시장의 사건을 중심으로 쓰며 억지로 한국 사실로 바꾸지 않는다. 이슈 분석·예상 시나리오·수혜 섹터·피해 섹터·연관 섹터·리스크 체크리스트·주요 일정은 항상 **한국 상장기업과 국내 섹터의 관점**이다. 예: 엔비디아 실적은 핵심 사실, 국내HBM/후공정의 제품·고객·수요 연결과 불확실성은 한국 영향 분석이다. 국내 전달 근거가 없으면 해외 가격 급등만으로 게시하지 않는다.

기사 버전에는 `selection_market_basis(KR/FOREIGN_US), source_market, evidence_as_of, analysis_perspective=KR_EQUITY, impact_profile, visibility_policy_version`을 저장한다. 홈 스냅샷의 현재 market_basis는 별도다.09:10/20:00이 됐다는 이유로 기사를 다시 게시하거나 source_market/최초일을 바꾸지 않는다. 새 사건/근거 없이 기존 본문을 재작성하지 않는다. 해외 비교군과 시트 연관기업은 탐색 도구이며 국내 기업 영향 근거를 대신하지 않는다.

### 기사별 상세 영역 노출 {#article-visibility}

같은 템플릿을 사용하되 모든 영역을 채우지 않는다. 공통 필수는 기사 상단·핵심 이슈·한국 관점 이슈 분석·출처이고 선택 영역은 아래 결정표로 산출한다. 빈 제목·빈 구분선·‘등록된 정보 없음’ 자리 채움 문구를 표시하지 않는다. 부정 시나리오만 단독 표시하지 않는다.

| 근거 기반 분석 상태 | 예상 시나리오 | 섹터·리스크 노출 |
| --- | --- | --- |
| 유효한 긍정 경로만 있음 | 긍정만 | 수혜/연관은 각각 해당 근거가 있을 때만, 피해는 없음. 리스크도 실제 체크할 내용이 있을 때만 |
| 유효한 긍정과 부정 경로 모두 있음 | 긍정·부정 | 각 방향의 예상결과·체크사항을 구분하고 해당 섹터만 노출 |
| 피해만 확인되고 유효한 긍정 경로 없음(DAMAGE_ONLY) | 전체 미노출 | 피해 섹터와 리스크 체크리스트 노출. 수혜를 만들지 않으며 부정 예상결과/확인 조건은 리스크에 통합 |
| 직접 호재·피해로 단정할 수 없으나 실제 국내 연결 있음(RELATED_CONDITIONAL) | 근거 있는 조건부 긍정 또는 긍정·부정 | 연관 섹터로 노출. 방향을 사실로 단정하지 않고 조건/불확실성 명시 |

서버의 방향 판정은 검증된 영향 경로를 먼저 구조화한 뒤 결정한다. `positive_path`는 BENEFIT 근거 또는 검증된 조건부 긍정 경로, `negative_path`는 DAMAGE 근거 또는 검증된 조건부 부정 경로의 존재다. 둘 다 있으면 POSITIVE_NEGATIVE로 긍정·부정을 함께 표시한다. BENEFIT과DAMAGE가 동시에 있으면 서로 다른 섹터/경로여도 반드시 이 규칙이며 긍정만으로 축소하지 않는다. 긍정만 있으면 POSITIVE_ONLY(피해 섹터 없음), 긍정 없이DAMAGE가 있으면 DAMAGE_ONLY로 시나리오를 숨긴다. 직접BENEFIT/DAMAGE 없이RELATED만 있으면 RELATED_CONDITIONAL로 두고 positive_path/negative_path 조합에 따라 긍정만/양쪽/미노출을 산출한다. 직접 피해 없이 부정 조건만 있는 경우도 시나리오는 숨기고 검증된 연관/리스크에 설명한다. 별도의 부정 단독 시나리오나 임의 예외는 두지 않는다. 이 판정은 LLM의 시나리오 문장 유무가 아니라 근거 ID가 붙은 영향 경로에서 산출하고 이후 문장을 작성한다.

RELATED_CONDITIONAL에서조차 근거 있는 긍정 경로가 없으면 긍정을 창작하지 않고 예상 시나리오는 숨긴다. 확인된 연관과 리스크만 설명할 수 있다. 이는 연관 섹터를 무조건 수혜로 바꾸지 않는 안전 조건이다. DAMAGE_ONLY의 리스크는 실제 피해의 지속·확대·해소를 확인할 항목을 근거로 작성하며 내용 없이 게시 형식만 채우지 않는다.

수혜/피해는 국내 사업·수요·원가·규제 등 방향과 전달 경로의 근거가 충분한 경우, 연관은 연결은 확인됐으나 방향/규모/조건이 미확정인 경우다. 여기서 확실한 호재·피해는 **영향 방향의 근거**를 뜻하며 주가 상승/하락 확정이나 수익 보장이 아니다. 같은 섹터·동일 영향 경로를 세 영역에 중복 배치하지 않는다. 서로 다른 경로는 구분 설명·근거를 두고 표시할 수 있다. `related_sector_ids`는 필터/관심알림 연결의 상위 집합이며 화면의 연관 섹터 목록과 같다고 가정하지 않는다. `impacts[].direction=BENEFIT/DAMAGE/RELATED`·한국 섹터/기업·경로·근거 ID·조건으로 표시 목록을 별도 산출한다.

주요 일정은 **해당 기사 이후 국내 영향 판단을 위해 실제 확인할 발표·시행·실적·행사**가 있고 시각/기간·시간대·공식/검증 근거가 있을 때만 표시한다. 해외 행사도 한국 영향 체크 대상이면 포함한다. 이미 끝난 사건 날짜나 막연한 ‘향후 확인’은 일정 칸을 만들지 않는다. 발표일은 미정이나 공식 예정기간이 확인되면 그 기간과 미확정 사실을 명시한다. 시간 경과/취소/정정 시 재검증해 지난 항목은 향후 일정에서 제거한다.

표시용 `visible_sections`는 서버가 최신 공개 article_version·검증 근거·visibility_policy_version으로 계산하고 관리자 미리보기와 Android/iOS가 같은 계약을 사용한다. 클라이언트의 임의 숨김만으로 잘못된 생성 데이터를 통과시키지 않는다. 선택 영역만 근거가 없으면 그 영역을 제외하고, 핵심 사실/한국 영향이 무너지면 기존 게시 차단·정정 절차를 적용한다. 시간 경과에 따른 일정 제거는 표시 갱신이며 최초 게시일을 변경하지 않는다. 본문 실질 변경은 새 버전·감사 이력으로 처리한다.
